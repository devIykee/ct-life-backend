# Wallet sign-in and explicit login identities

EVM and NEAR players can create a CT Life player UUID without a Solana wallet. Existing SIWS users keep their UUID, character, inventory and primary Solana wallet. `users.wallet` and access-token `wal` are nullable; null is not an address and grants no Solana-specific entitlement. Payment-wallet links remain a separate identity proof for payment attribution. They never become sign-in credentials implicitly.

## Signing contract

Primary sources checked 2026-11-05: [EIP-4361](https://eips.ethereum.org/EIPS/eip-4361) defines the SIWE message, checksum address, chain, nonce and EIP-191 EOA verification; [NEP-413](https://github.com/near/NEPs/blob/master/neps/nep-0413.md) defines the recipient, 32-byte nonce, optional callback, tagged Borsh payload and FullAccess signature. Existing pinned `viem` and Node Ed25519 verification are reused; no new dependency, live signing or funds transfer is involved.

The new routes support `eip155:4663` EOAs and `near:mainnet` accounts with an Ed25519 FullAccess key. EIP-1271/EIP-6492 smart-contract signatures are not supported. NEAR ownership is checked against a configured mainnet RPC at finalized state on each login/enrolment proof; pending, unavailable, FunctionCall and removed keys fail closed. A session records the identity used at login; refreshing it does not perform a continuous NEAR key-state subscription or sign a new proof.

- Anonymous `POST /v1/auth/wallet/challenge` accepts exactly `{network,address}` and returns 201.
- Authenticated `POST /v1/auth/identities/challenge` accepts the same body for explicit enrolment into the current UUID.
- Both return `{id,purpose,userId,network,address,proofScheme,nonce,message,domain,uri,issuedAt,expiresAt}`. `purpose` is `login` or `enrolment`; `userId` is null for login and the authenticated UUID for enrolment. Nonce is 64 lowercase hex characters; timestamps are ISO strings with milliseconds; TTL is five minutes.
- NEAR additionally returns `nearSignMessage:{message,nonceBase64,recipient,callbackUrl:null,state}`. The nonce decodes to the same 32 bytes; recipient is domain and state is challenge ID. Callback is explicitly Borsh `None`, never a client-supplied redirect.
- Corresponding `POST .../verify` accepts exactly `{challengeId,signature,publicKey?}`. EVM signature is 65-byte hex with no publicKey; NEAR uses canonical base64 signature and `ed25519:<base58>` publicKey. The server verifies its persisted message, never a submitted replacement.

The exact generated text lives in `server/application/wallet-auth.ts:createLoginMessage`. SIWE uses checksummed message address, chain 4663, request ID and expiry. Login statement:

> Sign in to CT Life. This proves account access only; it does not authorize payments or transactions.

Login resource is `urn:ctlife:purpose:login`. Enrolment statement:

> Add this wallet as a sign-in identity for CT Life player {userId}. This grants access to that player account; it does not authorize payments or transactions.

Enrolment resources are `urn:ctlife:player:{userId}` followed by `urn:ctlife:purpose:enrolment`. NEAR signs the same statement in explicit domain/account/network/purpose/player/URI/request/nonce/time lines. Browser guards reconstruct and compare the entire message before requesting a signature. Wallet-link proofs retain their different statement and purpose.

## Sessions, ownership and retries

Login returns existing `{accessToken,refreshToken,user}` plus the legacy flat fields. Both flat and nested user fields include nullable `wallet`, `authMethod` (`siws`, `dev`, `wallet`) and `loginIdentity:{id,network,address}`, `loginIdentityVersion` (nonnegative integer) and `authenticatedAt` (original Unix seconds or null when legacy evidence is unknown). Refresh returns the same identity and method; JWT `lid`, `liv` and `am` carry the credential, generation and method in both token types. Missing legacy `liv` is exactly zero, never the current database generation. Pre-migration refresh tokens can resolve only their owner's existing primary Solana identity. Refresh remains single-use. Signed `auth_time` records the original verified sign-in and is copied unchanged into both rotated tokens. Legacy tokens without it remain unknown; refresh never upgrades `iat` into authentication evidence. Deleted or banned users cannot sign in or rotate sessions.

Both enrolment challenge and verification require a verified sign-in within ten minutes, allowing at most 30 seconds of future clock skew. Missing or stale `auth_time` returns `403 AUTH_REAUTH_REQUIRED`; sign in to the existing player account again before adding a credential. A dev login qualifies only while explicitly enabled in local/mock scope. The ten-minute threshold is CT Life policy, informed by [OWASP’s requirement for re-authentication before sensitive account changes](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#require-re-authentication-for-sensitive-features), not a timing requirement imposed by that standard.

Enrolment verification returns `{identity:{id,network,address,createdAt}}`. Both stages persist/recheck the authenticated initiator identity and generation under the player lock. Another credential on the same account cannot finish that ceremony. `GET /v1/auth/identities` lists only active sign-in methods and adds `securityEvents`, the latest twenty owner-scoped events ordered by timestamp and ID descending. Events contain `{id,identityId,kind,network,createdAt}` only; no wallet address, token, signature or nonce. They are notification/history data, never authentication authority.

## Credential removal and sessions

`DELETE /v1/auth/identities/{id}` removes an EVM/NEAR login method. Recent original authentication with a different retained credential is required; the last usable login method cannot be removed. The primary Solana identity is immutable in this slice. Unknown/unowned IDs return `AUTH_IDENTITY_NOT_FOUND` (404); current credential, last credential and primary removal use `AUTH_USE_ANOTHER_IDENTITY`, `AUTH_LAST_IDENTITY` and `AUTH_PRIMARY_WALLET_IMMUTABLE` (409). Missing/stale authentication remains `AUTH_REAUTH_REQUIRED` (403). Repeated removal of an owned revoked identity returns 204 without another version bump.

Removal sets `revoked_at` and increments `session_version`, retaining address ownership. Anonymous sign-in cannot reactivate it or create another account. An explicit fresh enrolment by the same owner can reactivate it without resetting its version. Old access/refresh tokens remain rejected with `AUTH_IDENTITY_REVOKED` (401). Revocation also consumes pending proofs targeting that identity or initiated by its previous generation. Payment links, inventory and historical financial obligations are unchanged.

REST authorization, refresh and token minting check active credential generation against PostgreSQL. Unavailable account state returns `503 AUTH_STATE_UNAVAILABLE`; clients retain credentials. JWT/revoked-credential rejection remains terminal 401. Refresh performs durable reads before reserving its single-use marker, never retries the transaction across that external reservation, and compare-deletes only its own unreturned failed issuance marker. Successful issuance and concurrent-replay protection remain single-use. A failure to clean up an uncertain Redis reservation can still require explicit sign-in; delivery loss never authorizes a client to guess new tokens. Enrolment and removal repeat that check inside the user-locked mutation, including requests which passed middleware before a concurrent removal. Realtime carries resolved credential context and uses targeted revocation events plus durable batched checks; checks run every 15 seconds with a five-second outer authority deadline. A timed-out check closes only captured sessions with code 4006, retains the no-overlap lock until its underlying query settles, and ignores late results or replaced scopes. Event publication failure does not undo a committed revocation. Newly authorized requests are refused durably; a request admitted before removal can already be in flight. A submitted chain transaction is not cancelled by removing a sign-in method.

**Media limitation:** separately issued LiveKit tokens and established media connections use their own lifecycle. This credential change does not claim instant revocation of every existing media connection or token. Credential-aware media enforcement requires its own integration and acceptance checks; fresh token requests remain protected by REST authentication.

## Explicit primary Solana attachment

`POST /v1/auth/primary-solana/challenge` accepts exactly `{address}` for a recently authenticated current player. It returns existing challenge fields with purpose `primary-solana-enrolment`, network `solana:mainnet`, scheme `siws-ed25519` and a non-null owner UUID. The five-minute proof binds the initiating credential generation, canonical on-curve public key, current origin/domain/URI, request ID and random nonce. The exact message is generated by `wallet-auth-lifecycle.ts:createPrimarySolanaMessage`; its statement explicitly grants primary-wallet and sign-in access to that player, with player and purpose resources. [Official SIWS fields](https://github.com/phantom/sign-in-with-solana) and [Phantom domain/URI validation](https://docs.phantom.com/developer-powertools/signing-a-message) informed this separate signing purpose. Payment-link signing guards are unchanged.

`POST /v1/auth/primary-solana/verify` accepts exactly `{challengeId,signature}`, where the signature is canonical base64 Ed25519 over the stored UTF-8 message. It returns `{userId,challengeId,wallet,identity:{id,network,address,createdAt}}`. The server checks current credential/recent auth again, consumes the proof once, and attaches to the existing UUID only. An existing different primary yields `AUTH_PRIMARY_WALLET_EXISTS` (409); another active player's primary, login identity or unreleased payment reservation yields `AUTH_IDENTITY_CONFLICT` (409). Shared address → player → challenge locks serialize this with legacy SIWS signup. No account merge, primary replacement or automatic payment link occurs. Existing SGT lookup/uniqueness rules apply; unavailable evidence leaves non-Seeker status.

A later SIWS login resolves this same UUID. The current EVM/NEAR session retains its original authenticating identity, generation and authentication time. **The current client ordinary-refresh guard rejects any primary change, including null→address.** Only a matching verified ceremony may authorize a private owner/revision/generation/address-bound session transition. Do not relax normal refresh or infer this authorization from `/me`. Serialize verify/scoped refresh against ordinary refresh, consume its allowance once, preserve pending-payment journals, and discard stale callbacks. A lost verification response requires explicit retained-credential sign-in to recover current state, not replaying the consumed proof or guessing attachment succeeded. SOL/ORE spending still requires the separate payment-wallet link and actual wallet authorization.

A valid payment link belonging to an active player, including a revoked payment link, blocks anonymous creation with `409 AUTH_IDENTITY_ENROLMENT_REQUIRED`. Sign in to that existing player first and enrol explicitly. An identity owned by another player gives `409 AUTH_IDENTITY_CONFLICT`. New login claims and payment-link claims share a PostgreSQL address lock, then user and challenge locks. Database uniqueness is the final same-table constraint. Valid successful/conflicting proofs are consumed; replay/expiry/wrong purpose or owner returns `AUTH_CHALLENGE_INVALID`. Wrong origin gives `AUTH_ORIGIN_INVALID`; invalid signature gives `AUTH_PROOF_INVALID`. All issuance and verification use the existing per-IP login limit; verification also holds the global login semaphore. Anonymous issuance has no victim-address cap: unsigned requests cannot exhaust another wallet’s sign-in slots. Authenticated enrolment limits only the caller’s outstanding requests. Each issuance removes at most 100 expired rows using an expiry index and skip-locked selection.

A response lost after successful verification requires a fresh challenge/signature. The next login resolves the same durable identity and UUID; it cannot create a duplicate account. No anonymous token-response cache is introduced. Login identities authenticate account access only: every payment still requires its own explicit wallet authorization and verified receipt.

## Deletion and migration compatibility

Migration 153 makes the Solana field nullable and backfills existing Solana identities. Apply it before code that queries the new tables. Do not route non-Solana clients to older backend binaries that require a non-null wallet. Old SIWS writers remain address-compatible; a new verifier creates a missing explicit Solana identity for a legacy row. The payment-link unique index changes to a partial current-owner index: old payment writers using `ON CONFLICT(network,address)` without its predicate are incompatible after migration 153. Coordinate the writer cutover; this is not a mixed-version rolling release guarantee. No deployment is performed here.

Account deletion preserves the established fresh-signup policy. It deletes login identities/challenges and account-access events, invalidates outstanding proofs bound before the first ownership claim, clears the primary wallet and releases/revokes payment links. Original link IDs, order UUIDs and refund/receipt ownership remain attached to the deleted UUID. A fresh signature can create a new UUID and a newly verified payment link with the same address; it cannot access old inventory or transfer historical obligations. Active-owner payment revocation does not release ownership. Authorized REST requests and realtime joins check durable active-account state even if the Redis deletion flag is missing.

Migration154 retires old authenticated challenges without an initiator binding, adds credential generations and retained revocation state, expands only the new primary-Solana purpose, and adds account-access events. Apply it before lifecycle-aware code. All API/realtime readers must enforce generations before removal is exposed; older readers which ignore revocation cannot remain in the serving pool. Old authenticated-enrolment writers without initiator fields are incompatible with the new constraint. Coordinate the writer/readers cutover; no mixed-version revocation guarantee is claimed. Migration154 rollback refuses used versions/revocations or retained security events instead of reviving tokens.

Migration153 rollback refuses null-wallet accounts, non-Solana enrolled identities or repeated payment-address history. It does not discard an account or retained evidence to fit the old schema. Migration was exercised only on the disposable local economy database; no deployment or external migration is part of this change.

## Validation and limits

Generated-signature PostgreSQL/HTTP regressions cover new/returning login, concurrent claims, payment-link conflicts, explicit enrolment, origin/purpose/expiry/replay rejection, NEAR key permissions, ban/deletion, refresh rotation, legacy SIWS/SGT eligibility, and non-Solana `/me` → birth lottery → character creation. Additional generated-signature tests cover mutual removal races, revoked/re-enrolled generations, initiator binding, lost pubsub, retained payment ownership, primary/legacy-SIWS races, strict Solana proof scope, SGT failures/conflicts, stable UUID/inventory/balance, deleted-owner history and guarded rollback. Fixtures call no external chain or real wallet. Browser/API contract fixtures cover both signing formats and purposes. Native APK EVM/NEAR wallet transport and live wallet acceptance are separate, unverified work; this backend does not claim those journeys work.
